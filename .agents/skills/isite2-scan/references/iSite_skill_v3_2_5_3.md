# iSite Skill v3.2.4

> 目标：用公开证据、分场景客观建模、交叉校验、需求链路和可审计推测，完成高价值楼宇/场景的**全量扫描、证据筛选、室分机会识别、现网状态判断、方案建议和多格式输出**。

---

## A. 这份 skill 的定位

这不是报告模板，而是一套**执行规范 + 数据契约 + 多 agent 工作流协议 + 规则库**。

它服务于四类核心任务：
1. 把候选池找全。
2. 用分场景客观证据证明哪些目标是真正的高价值楼宇。
3. 用需求链路解释为什么该建室分、适合什么方案。
4. 把结果输出成适合售前、投标、研究或管理决策的结构化交付件。

这版重写的目标只有一个：**在不删减任何信息点和硬要求的前提下，把规范改造成更顺的主流程、更清晰的阶段门、更稳定的数据契约，以及更适合多 agent 拆分的模块结构。**

---

## B. 执行总则

### B1. 不可改变的硬原则
- 全量扫描优先：用户要求“全量扫描”时，候选池不设数量上限；Top N 只能作为展示视图，不能反向裁剪底池。
- 证据优先于判断：所有高价值判断都必须能回到原始事实、来源、日期和假设；没有证据，不下强结论。
- 场景优先于统一评分：不同场景使用不同的高价值证明逻辑；默认不使用跨国家、跨场景统一总分作为主结论。
- 高价值证明链与现网建设状态是两条不同证据链：楼宇高价值已验证，不代表其已建室分也已验证。
- 允许保守推测，但必须显式留痕：推测只能补字段和辅助筛选，不能伪装成直接事实。
- 主表去重复：主表只保留单点差异与关键结果；通用规则、公式、定义统一收进 `Method / Parameters / Legend / Model Detail`。
- 结果必须可审计：任一结论都必须能拆解为 `原始事实 -> 证据等级 -> 场景证明链 -> 需求推导 -> 现网状态判断 -> 方案建议 -> 下一步动作`。

### B2. 适用任务
默认适用于：
- 国家级 / 区域级 / 城市级高价值楼宇全量扫描
- 高价值物业 shortlist
- 基于证据筛选高价值楼宇
- 室分机会识别
- 现网是否已建室分判断
- 传统 / 数字化室分判断
- 4G / 5G / 4G+5G 室内制式判断
- 单点洞察卡 / 投标前洞察卡
- 按自定义规则筛选目标楼宇
- 按自定义格式输出表格、PPT、Markdown、清单

不适用于：
- 纯技术设计图纸输出
- 精确工程预算
- 已建网络现网参数优化
- 需要工程级覆盖仿真的任务
- 没有明确物业实体、只有模糊片区名的任务
- 需要替代现场勘察的任务

## C. 多 agent 工作流

### C1. 标准角色拆分
1. **Scope Agent**：明确边界、国家名单、城市口径、输出形式、自定义规则。
2. **Discovery Agent**：按场景全量建候选池。
3. **Entity Agent**：统一名称、地图位置、经纬度、地理定位精度。
4. **Evidence Agent**：收集核心事实、来源、日期、来源等级。
5. **Scene Modeling Agent**：按场景提取主指标、辅助指标、面积/尺度字段、代理逻辑。
6. **Build Status Agent**：单独判断是否已建室分、系统类型、网络制式。
7. **Demand Agent**：计算日均到访、忙时用户、忙时流量、忙时带宽。
8. **Inference Agent**：在直接证据不足时执行保守推测，并完成显式留痕。
9. **Conclusion Agent**：输出 `Evidence Status / Value Class / Action Class / Recommended Solution`。
10. **Output Agent**：生成主表、证据表、明细表、PPT、Markdown、清单等交付件。
11. **QA Agent**：检查字段完整性、证据冲突、推测越权、主表去重复、格式一致性。

### C2. 协作协议
- 各 agent 只处理本模块内的问题，不混做结论。
- 上游输出必须结构化，下游不得靠自由文本猜含义。
- 任一 agent 若发现冲突或缺口，应写入 `Issue / Review Queue`，而不是静默跳过。
- 所有推测必须由 `Inference Agent` 统一登记，不允许在其他模块里偷偷推断。

## D. 主流程与阶段门

### D1. 输入
最小输入包括：
- 扫描范围：国家 / 区域 / 城市
- 是否全量扫描
- 用户自定义筛选规则（如有）
- 输出形式
- 是否需要单点洞察卡 / PPT

### D2. 默认输出
默认至少输出：
- `Main`
- `Evidence`
- `Model Detail` 或 `Scoring/Reasoning Detail`
- `Parameters`
- `Review Queue`
- `Method`
- `Legend`
- `Country Summary`（批量扫描时）

### D3. 阶段门
每个物业点必须依次通过：
1. **实体门**：名称、国家/城市、地图位置、场景可归类。
2. **证据门**：至少有 1 条 Tier 1 / Tier 2 来源，或 2 条独立 Tier 3 来源；至少有 1 个场景核心指标或强代理指标。
3. **场景建模门**：正确场景模型、`Proxy Basis`、`Proxy Level`、场景适配面积/尺度字段齐备，或显式标注 `Unknown / Inferred / Proxy`。
4. **现网状态门**：必须输出 `Indoor System Presence / Indoor System Type / Indoor RAT / Build Evidence Status`，即使无直接证据也不得留空。
5. **需求链路门**：若核心规模指标足够，必须计算需求链路；不足则必须写明无法计算原因。
6. **结论门**：必须输出 `Evidence Status / Value Class / Action Class / Recommended Solution` 或保守留空说明。

## E. 模块清单

### E1. 候选池模块
- 当用户要求“全量扫描”时，候选池不设数量上限。
- Discovery Agent 必须覆盖所有优先场景。
- 不得因为“公开资料不好找”而提前截断某一类场景。
- 不得只抓最知名地标后就停止。
- Top N 只能作为展示层，不得改变底池。

默认优先扫描场景：
- 机场航站楼
- 国际会展中心 / 会议中心
- 体育场 / 体育馆 / 赛事综合体
- 高端酒店 / 会奖酒店
- 区域级 mall / mixed-use 综合体
- CBD 地标办公楼 / 金融中心 / 总部园区
- 高流量轨交换乘枢纽
- 医院核心楼宇
- 大学校园核心楼宇
- 港口 / 邮轮码头
- 政府综合体 / 外交区综合体

场景定义：
- 体育场归为半开放场景。
- 其他典型楼宇内部场景默认归为纯室内场景。
- 轨交换乘枢纽的站台 / 站厅 / 通道属于其内部覆盖空间。

### E2. 数据契约模块
每个物业点必须遵守统一字段契约；所有详细字段和场景适配字段见附录 A。

### E3. 证据模块
必须使用来源分级、字段级证据状态、交叉校验、时间一致性和数值一致性规则；全部细则见附录 B。

### E4. 推测模块
允许推测的字段、推测前提、强制留痕字段、`Inference Chain` 写法和推测约束全部保留，见附录 C。

### E5. 分场景建模模块
每类场景的主指标、辅助指标、面积/尺度字段、高价值证明逻辑、交叉校验要点和复核触发条件全部保留；同时新增“分场景指标矩阵 + 可获取度分级”，见附录 D 与附录 M。

### E6. Proxy Basis 模块
定义、输出规则、Proxy Level、选择规则、冲突处理全部保留，见附录 E。

### E7. 需求链路模块
目的、公式、默认参数区间全部保留；仅用于解释需求，不包装成统一总分，见附录 F。

### E8. 结论模块
默认不输出统一总分；默认输出 `Evidence Status / Value Class / Action Class` 三类结论，并保留排序规则，见附录 G。

### E9. 现网建设状态模块
`Indoor System Presence / Indoor System Type / Indoor RAT / Build Evidence Status / 判断规则` 全部保留，见附录 H。

### E10. 方案推荐模块
保留“先判断是否值得建，再按场景形态选方案”的规则：纯室内高价值场景默认 `pRRU`，半开放场景默认 `hRRU`；输出规则与证据不足时的处理见附录 I。

### E11. 自定义筛选与输出模块
可自定义筛选条件、输出形式、输出件最小规范全部保留，见附录 J。

### E12. QA 模块
最小检查清单完整保留，见附录 K。

## F. 主表、明细表与接口规范

### F1. 主表只保留什么
- 物业基本信息
- 场景类型与形态
- 关键结果值
- 现网状态结果
- 方案结果
- 优先级 / 动作类结果
- 单点特有推荐理由
- 单点特有备注

### F2. 主表不应重复什么
以下内容不得逐行重复写入主表：
- 通用评分 / 结论解释
- 通用公式解释
- 方案定义
- 证据等级定义
- Proxy Basis 的长解释
- 容量等级定义

这些统一写入：
- `Method`
- `Parameters`
- `Legend`
- `Model Detail`
- `Evidence`

### F3. 多 agent 传递的最小数据包
每个物业点在模块间流转时，至少携带：
- 实体字段
- 场景字段
- 核心规模指标
- 证据来源链
- `Proxy Basis / Proxy Level`
- 现网状态字段
- 推测留痕字段（若有）
- 需求链路字段（若可计算）
- 结论字段

---

## G. 执行要求

- 先证据，后建模，后结论，后输出。
- 场景模型必须先于结论。
- 现网状态必须单独判断，不得由高价值结论代替。
- 推测只能补空，不能覆盖直接证据。
- 同类场景、同类证据结构下，`Proxy Basis` 应保持一致。
- 证据不足时，应进入 `Review Queue`，并写出具体复核动作，而不是写空泛套话。

## 附录 B. 证据规则库



### 7.1 来源等级

**Tier 1**
- 物业 / 运营方官网
- 年报 / ESG / 投资者材料
- 政府 / 监管 / 机场 / 地铁 / 场馆 / 卫健 / 教育官方公开材料

**Tier 2**
- 行业协会
- 权威咨询机构
- 交易所公告
- 对官方数字的高可信转述

**Tier 3**
- OTA / 地图平台 / 活动平台 / 地产平台 / 聚合站 / 新闻稿汇编

规则：
- Tier 1 可作主证据。
- Tier 2 可补强或校验。
- Tier 3 只能辅助，不单独决定高价值结论。

### 7.2 每条关键事实的最小证据字段
- `Indicator Name`
- `Indicator Value`
- `Unit`
- `Source Name`
- `Source Tier`
- `Source Date`
- `Direct / Proxy / Inferred`
- `Assumption Note`

### 7.3 交叉校验（强制）

凡用于证明高价值或判断现网状态的核心指标，优先做交叉校验。

优先使用以下任一组合：
- `1 条 Tier 1 主证据 + 1 条 Tier 2 / Tier 3 辅证据`
- `2 条独立 Tier 2 证据`
- `1 条 Tier 1 直接值`（若是官方核心值且场景非常明确）

交叉校验必须覆盖的典型指标包括：
- 机场旅客吞吐量
- 国际旅客占比
- 体育场座位数
- 上座率 / 活动天数 / 大型赛事频率
- 会展面积 / 年活动数 / 参会人数
- 酒店房量 / 会议面积 / 会奖能力
- mall GLA / 客流 / 旗舰定位
- 办公楼面积 / 租户质量 / 总部密度
- 医院床位 / 门诊量
- 大学校园人数 / 核心设施使用强度
- 枢纽日均客流 / 换乘量
- 是否已建室分
- 室分类型（传统 / 数字化 / 混合）
- 室分网络制式（4G / 5G / 4G+5G）

### 7.4 时间一致性
- 尽量使用同年度或相邻年度数据。
- 若年份不一致，必须写清年份。
- 若使用疫情期或极端年份，必须注明，不得默认为常态值。

### 7.5 数值一致性
- 多来源差异较小，可判为一致。
- 若关键指标差异明显，必须标记 `Evidence Conflict` 并进复核。
- 无法确认哪个更可信时，以更保守值作为暂用值，并说明。

### 7.6 证据状态（强制）
- `Verified / 已验证`：核心字段已有直接证据，或已有强交叉校验，足以支撑主表结论。
- `Supported / 已支撑`：已有主证据或强 Proxy 支撑，但交叉校验仍不完整，适合进入候选池和进一步核验。
- `Indicative / 指示性`：只有弱证据、单条辅助来源或推测链路，足以提示关注，但不足以下强结论。
- `Insufficient / 证据不足`：证据明显不足，只能进入复核或观察。

### 7.7 字段级证据状态（强制）
以下字段应尽量给出字段级状态：
- `Area Metric Status`
- `Build Evidence Status`
- `Indoor System Presence`
- `Indoor System Type`
- `Indoor RAT`

规则：
- 一个物业点可以 `Evidence Status = Verified`，但 `Indoor System Type = Unknown`。
- 不要因为楼宇价值已验证，就默认现网状态也已验证。

## 附录 C. 推测与留痕规则库



### 8.1 允许推测的字段
- `Area Metric Value`
- `Indoor System Presence`
- `Indoor System Type`
- `Indoor RAT`
- 其他能由相邻公开事实保守外推的字段

### 8.2 推测前提
必须同时满足：
- 至少有 1 条与该字段直接相关或高度相关的公开来源
- 推测链路不超过 3 步
- 推测方向保守，不夸大
- 不与直接证据冲突

### 8.3 强制留痕字段
只要使用推测，必须同时输出：
- `Inference Flag = Yes`
- `Inferred Fields`
- `Inference Chain`
- `Inference Note`
- `Inference Confidence`（Conservative / Moderate）

### 8.4 `Inference Chain` 写法
统一写成：
`Observed facts -> intermediate judgment -> inferred field`

例如：
- `Observed: flagship international terminal + operator 5G airport announcement -> likely indoor multi-RAT requirement -> Indoor RAT = 4G+5G (Inferred)`
- `Observed: stadium seat count + event calendar + repeated sold-out reports -> likely high event attendance -> occupancy proxy inferred`

### 8.5 推测约束
- 推测不能伪装成直接值。
- 推测不能覆盖冲突的直接证据。
- 推测只能帮助补字段和筛选，不得把弱证据包装成强结论。
- `Indoor System Type` 的推测必须特别保守；没有明确架构线索时，宁可写 `Unknown`。
- `Indoor RAT` 的推测也必须保守；只有存在运营商 / 业主 / vendor 公开线索时，才可从 `4G` 推到 `4G+5G`。

## 附录 D. 分场景客观建模规则库



> 原则：不同场景必须使用不同的高价值证明指标。
> 先看主指标，再看辅助指标，再看战略角色。
> 不得把“地标、豪华、热门”这类模糊描述当主证明。

### 9.1 机场航站楼

**高价值主指标**
- 年旅客吞吐量

- 国际旅客占比

**辅助指标**

**默认高价值证明逻辑**

- 国家级主门户机场或城市主门户机场
- 国际旅客占比高、出入境需求强
- 本国 / 本城市客流排名靠前的主航站楼
- 客流量大，且室内连续覆盖空间明确

**首选面积 / 尺度字段**
- `Terminal Area`
- 允许替代：航站楼 GFA / 候机区面积 / 旅客处理能力

**标准 Proxy Basis**
1. `Direct Observed Metric`
2. `Airport Passenger Throughput Proxy`
3. `Terminal Role × Airport Throughput Proxy`

**关键来源**

## 附录 E. Proxy Basis 规则库



### 10.1 定义
`Proxy Basis` 用来说明：当缺少直接运营数据时，这个物业点的规模 / 流量 / 需求强度是基于什么客观代理逻辑估算的。

### 10.2 输出规则
- `Proxy Basis` 只能使用标准字典，不得自由发挥改写。
- 同类场景优先使用同一条标准 `Proxy Basis`。
- 若使用回退代理，必须同时填写 `Proxy Level` 和 `Assumption Note`。
- 若拿到直接运营数据，`Proxy Basis = Direct Observed Metric`。
- 主表中 `Proxy Basis` 只写标准短语；详细解释写到 `Method / Evidence / Model Detail`。

### 10.3 Proxy Level
- `P0 Direct`
- `P1 Strong Proxy`
- `P2 Moderate Proxy`
- `P3 Weak Proxy`

规则：
- `P0`、`P1` 可进入正式筛选。
- `P2` 可筛选，但优先进入复核。
- `P3` 不能作为高置信直推的唯一依据。

### 10.4 选择规则
- 优先选与场景最接近的一阶代理，不得跨场景混用。
- 能用吞吐量，不用模糊“地标性”；能用座位 / 房量 / GLA / 床位 / NLA，就不用泛泛“人流大”。
- 同一国家同类资产，除非证据结构明显不同，否则 `Proxy Basis` 应保持一致。
- 同一物业点只允许 1 个主 `Proxy Basis`；辅助依据写入 `Assumption Note`。
- 若代理链条跨两步以上，必须降为 `P2 Moderate`。

### 10.5 冲突处理
出现以下情况必须复核：
- 同类场景在两次洞察中使用不同 `Proxy Basis` 且无理由
- `Proxy Basis` 与场景类型不匹配
- `Proxy Basis` 与核心规模量级明显不一致
- 使用 `P2 / P3` 代理却给出强推荐

## 附录 F. 需求链路规则库



### 11.1 目的
需求链路用于说明：
- 楼宇室内需求是否足够强
- 高峰容量是否足以支持室分建设
- 为什么更适合 pRRU / hRRU

### 11.2 公式（强制）
1. `daily_visits = annual_visits / 365`
2. `busy_hour_users = daily_visits × attach_rate × indoor_capture × busy_hour_factor`
3. `busy_hour_traffic_gb = busy_hour_users × gb_per_user_busy_hour`
4. `busy_hour_bandwidth_mbps = busy_hour_traffic_gb × 1024 × 8 / 3600`

规则：
- 不允许跳过派生过程直接手填忙时流量。
- 所有派生值都必须能追溯回原始值和参数。
- 默认不把需求链路转成跨场景统一总分。

### 11.3 默认参数区间

| 场景 | attach_rate | indoor_capture | busy_hour_factor | gb_per_user_busy_hour |
|---|---:|---:|---:|---:|
| 机场航站楼 | 0.75–0.85 | 0.85–0.95 | 0.08–0.12 | 0.45–0.65 |
| 国际会展/会议中心 | 0.70–0.85 | 0.80–0.95 | 0.10–0.20 | 0.40–0.70 |
| 体育场馆 | 0.75–0.90 | 0.55–0.80 | 0.18–0.35 | 0.50–0.90 |
| 高端酒店 / 会奖酒店 | 0.60–0.80 | 0.75–0.90 | 0.06–0.12 | 0.30–0.55 |
| CBD办公 / 总部楼宇 | 0.65–0.85 | 0.80–0.95 | 0.10–0.18 | 0.35–0.60 |
| 区域级 mall / mixed-use | 0.65–0.85 | 0.80–0.95 | 0.10–0.18 | 0.35–0.60 |
| 医院 / 大学校园核心楼宇 | 0.60–0.80 | 0.80–0.95 | 0.08–0.15 | 0.30–0.50 |
| 轨交换乘枢纽 | 0.70–0.85 | 0.85–0.95 | 0.10–0.20 | 0.35–0.60 |

规则：
- 默认取区间中位值。
- 若使用项目化参数或国家级 DOU 研究替代，必须写入 `Parameters`。
- 半开放体育场的 `indoor_capture` 可显著低于纯室内场景。

## 附录 G. 结论规则库



### 12.1 默认不输出统一总分
除非用户明确要求，否则默认不输出跨场景、跨国家统一总分。

### 12.2 默认输出三类结论

#### `Evidence Status`
- `Verified`
- `Supported`
- `Indicative`
- `Insufficient`

#### `Value Class`
- `National Flagship`
- `City Core`
- `Regional Anchor`
- `Local Candidate`
- `Observation`

#### `Action Class`
- `Direct Recommend`
- `Survey First`
- `Review Queue`
- `Monitor`

### 12.3 判定逻辑

**Direct Recommend**
同时满足：
- `Evidence Status = Verified` 或强 `Supported`
- 具有明确场景高价值证明
- 物业实体清晰、位置清晰、场景清晰
- 容量需求和建设必要性明确

**Survey First**
适用于：
- 高价值特征很强
- 但缺 1–2 个关键可建性事实
- 或存在年份不一致 / 小范围冲突

**Review Queue**
适用于：
- 证据冲突
- 关键指标缺失
- 名称 / 坐标 / 场景不稳定
- 在建 / 规划 / 未投运

**Monitor**
适用于：
- 战略价值可能高
- 但当前公开证据仍弱
- 不适合立即推进

### 12.4 排序规则
如需排序，默认顺序为：
1. `Value Class`
2. `Evidence Status`
3. 场景主指标
4. 来源新鲜度

规则：
- 不要把不同场景的不同指标强行压成统一分值。
- 同一场景内部可按主指标排序。
- 跨场景展示时，以分层和证据状态为主，而不是伪精确总分。

## 附录 H. 现网建设状态规则库



### 13.1 `Indoor System Presence`
允许值：
- `Confirmed Present`
- `Confirmed Absent`
- `Likely Present`
- `Likely Absent`
- `No Public Evidence`
- `Planned / Under Construction`
- `Unknown`

### 13.2 `Indoor System Type`
允许值：
- `Traditional DAS`
- `Digital DAS`
- `Hybrid DAS`
- `Small Cells / Other Indoor System`
- `Unknown`

### 13.3 `Indoor RAT`
允许值：
- `4G`
- `5G`
- `4G+5G`
- `Multi-RAT Legacy`
- `Unknown`

### 13.4 `Build Evidence Status`
允许值：
- `Verified`
- `Supported`
- `Indicative`
- `Unknown`

### 13.5 判断规则
- `Confirmed Present / Confirmed Absent` 只用于有直接或强交叉证据的情况。
- `No Public Evidence` 不等于 `Confirmed Absent`。
- 若只有“室内覆盖”“网络升级”“信号改善”等泛化说法，`Indoor System Type` 默认 `Unknown`。
- 只有出现 `digital DAS / active DAS / shared indoor / centralized indoor / digital indoor system / digital distributed system` 等明确线索时，才可确认或保守推测 `Digital DAS`。
- 只有出现 `passive DAS / leaky feeder / legacy DAS / repeater / passive indoor system` 等明确线索时，才可确认或保守推测 `Traditional DAS`。
- 对 `Indoor RAT` 的判断同样需要运营商 / 业主 / vendor 公开线索；否则宁可写 `Unknown`。

## 附录 I. 方案推荐规则库



### 14.1 先判断是否值得建
只有满足以下条件之一时，才进入方案推荐：
- `Action Class = Direct Recommend`
- 或 `Value Class` 高且容量需求明确
- 或场景为国家级门户 / 大型会展 / 大型体育场 / 高流量枢纽且证据较强

### 14.2 再按场景形态选方案

**纯室内高价值场景** -> `pRRU`
适用：
- 机场航站楼
- 会展中心

## 附录 M. 分场景指标矩阵 + 可获取度分级

> 用途：在不改变 v3.2.3 原有“分场景客观建模”规则的前提下，进一步明确哪些指标适合做国家级全量硬筛选，哪些更适合做增强证据或叙述表达。

## 附录 N. 推荐理由生成规则（强制）

### N1. 目标

`推荐理由` 不是主观评价，也不是重复主表字段。  
它的作用是：

- 把多个客观证据压缩成一句可读、可汇报、可人工快速判断的结论
- 让主表在不重复公式、不重复通用定义的前提下，保留“为什么推荐这个点”的最短表达
- 为后续 PPT 单点洞察卡、shortlist、国家汇总提供可直接复用的短句

### N2. 基本原则

推荐理由必须满足以下要求：

1. **必须基于证据**
   - 只能从当前物业点已经收集到的主证据、辅助证据、Proxy、现网状态、需求链路中提取
   - 不允许凭印象补写

2. **必须短句化**
   - 默认 1 句，最多 2 句
   - 主表中推荐理由不得写成长段说明

3. **必须单点化**
   - 只能写该物业点特有的价值驱动因素
   - 不得写所有点都能套用的通用套话

4. **必须与场景匹配**
   - 机场写机场逻辑
   - 体育场写体育场逻辑
   - 酒店写酒店逻辑
   - 不允许跨场景错配表达

5. **推测项不得伪装成已证实**
   - 如果推荐理由中使用了推测结论，必须显式带上“（推测）”或“待核验”
   - 不允许把推测写成已验证事实

### N3. 推荐理由的标准结构

推荐理由默认按以下顺序组织：

`场景核心价值 + 关键客观证据 + 室分建设相关性`

推荐写法示例：

- 机场：  
  `国家级国际门户机场，客流规模大，国际属性强，航站楼室内覆盖需求明确。`
- 会展中心：  
  `国家级会展场馆，展会面积大、活动频率高，短时高并发通信需求突出。`
- 体育场：  
  `国家级体育场，座位数大、赛事活动频繁，半开放高峰场景适合 hRRU。`
- mall：  
  `城市级旗舰商业体，GLA 大、客群层级高、周末峰值明显，适合优先建设室分。`
- 酒店：  
  `5星酒店，国际品牌，房量与会奖能力强，高价值商务与会务覆盖需求突出。`
- 办公楼：  
  `CBD 核心办公楼，租户质量高、楼宇等级高，深室内连续覆盖价值明确。`
- 医院：  
  `区域级大型医院，床位和门诊量高，连续可靠室内覆盖需求强。`
- 大学：  
  `核心高校校园楼宇，在校人口多、核心设施使用强，室内高密度需求明显。`
- 枢纽：  
  `核心换乘枢纽，客流与换乘强度高，站厅/通道连续覆盖必要性高。`

### N4. 推荐理由的证据抽取优先级

写推荐理由时，证据提取顺序固定如下：

#### 第一优先：场景一级主筛选指标
- 机场：客流量、航站楼角色、国际属性
- 体育场：座位数、活动天数、赛事等级
- 会展中心：面积、活动频率、展会等级
- 酒店：星级档次、品牌、房量、会奖能力
- mall：GLA、旗舰定位、品牌结构、商圈级别
- 办公：楼宇等级、NLA、租户质量、CBD 核心度
- 医院：床位数、门急诊量、等级
- 大学：在校人数、核心设施强度
- 枢纽：客流量、换乘量、线路数、枢纽角色

#### 第二优先：部署必要性证据
- 深室内
- 连续覆盖
- 多楼层
- 长连廊
- 半开放高峰
- 复杂站厅 / 看台 / 候机区 / 展馆结构

#### 第三优先：高价值证明增强项
- 国际属性
- 国家级 / 城市级门户属性
- 高端客群 / 政商属性
- 旗舰定位
- 多运营商共享价值

### N5. 酒店场景的强制规则

酒店场景的推荐理由必须优先使用以下证据：

1. **星级档次**
   - 超奢 / 5 星 / 高端商务酒店

2. **品牌**
   - 国际品牌 / 全国高端品牌 / 城市旗舰品牌

3. **房量**
   - 房量大说明基础住宿容量强

4. **会奖能力**
   - 宴会厅、会议厅、Ballroom、MICE 属性

酒店场景推荐理由禁止只写：
- “位置好”
- “人流多”
- “属于高端酒店”

必须至少写出：
- 星级档次或品牌
- 房量或会奖能力
- 室分需求原因

### N6. 推荐理由生成的禁止项

禁止出现以下问题：

1. **重复主表中已有字段**
   - 例如把“场景类型=机场、证据状态=已支撑”直接改写成一句废话

2. **重复通用定义**
   - 不要在推荐理由里解释什么是 pRRU、什么是已验证

3. **空泛套话**
   - 如：
     - `具有较高价值`
     - `具有较高建设意义`
     - `适合部署室分`
   - 这些都必须落回具体证据

4. **超长句**
   - 推荐理由不是摘要报告，不要写成 3 行以上

### N7. 推荐理由字段在主表中的位置与约束

主表中的 `推荐理由`：
- 必须独立成列
- 位于 `证据状态` 后、`下一步核验动作` 前
- 不允许为空；若证据极弱，则写：
  - `证据不足，暂不形成正式推荐理由`
  - 或 `高价值线索存在，但需补关键证据后再形成正式推荐理由`

### N8. 推荐理由与推测的关系

若推荐理由包含推测项，必须满足：
- 推测本身已在 `推测留痕` sheet 中登记
- 推荐理由中用语要保守，例如：
  - `预计`
  - `（推测）`
  - `待核验`
- 不允许推荐理由先于推测留痕独立存在

### N9. 推荐理由生成的默认流程

1. 先识别场景类型
2. 读取该场景的一级主筛选指标
3. 读取该点已验证/已支撑证据
4. 抽取 2–3 个最强证据
5. 增加 1 个与室分建设直接相关的部署必要性说明
6. 压缩成 1 句中文短句
7. 若使用推测项，显式加保守措辞
8. 输出到主表与场景分表

## 附录 P. G列主指标真实值优先规则（强制）

### P1. 目标

主表 G 列 `物业点重要证据` 的目标是：
- 用该场景**最重要、最强、最具体**的主指标，快速证明该点为什么值得进入候选池
- 让人工在不打开证据表的情况下，先看到最核心的价值证据
- 避免用 proxy 链路和二次加工结果污染主证据列

### P2. 允许写入 G 列的内容

G 列只允许写：
- 各场景的**一级主筛选指标**
- 或在直接值不可得时，写同一主指标的**保守推测值**，并在数字后显式写 `（推测）`

### P3. 禁止写入 G 列的内容

G 列禁止写：
- 年访问量 Proxy
- 忙时流量 Proxy
- 忙时带宽 Proxy
- attach_rate / indoor_capture / busy_hour_factor
- 长段式推荐话术
- “高价值”“重点项目”“重要资产”这类抽象词
- 两个以上不同层级指标混堆在一起

### P4. 场景写法规范

#### 机场
G列优先写：
- 年客流
- 国际旅客占比（若能直接拿到）
- 航站楼角色（可作为补充）

标准写法：
- `年客流：45,359,485人次（2024）`
- `年客流：5,200,000人次（2024，推测）`

#### 会展中心
G列优先写：
- 会展面积
- 会议面积
- 展览面积

标准写法：
- `会展面积：34,000㎡`
- `会展面积：17,000㎡（推测）`

#### 商场 / Mixed-use
G列优先写：
- GLA
- 商业面积

标准写法：
- `GLA：78,000㎡`
- `GLA：56,000㎡（推测）`

#### 体育场
G列优先写：
- 座位数

标准写法：
- `座位数：78,838座`
- `座位数：53,500座（推测）`

#### 酒店 / MICE
G列优先写：
- 品牌
- 档次（超奢 / 5星）
- 房间数

标准写法：
- `品牌：JW Marriott；档次：5星；房间数：150间`
- `品牌：Rosewood；档次：超奢（推测）；房间数：160间`

#### 办公 / 政府
G列优先写：
- 办公面积
- 楼宇等级（若办公面积缺失，可作为补充）

标准写法：
- `办公面积：45,000㎡`
- `办公面积：60,000㎡（推测）`

#### 医院
G列优先写：
- 床位数

标准写法：
- `床位数：647床`
- `床位数：370床（推测）`

#### 大学
G列优先写：
- 在校人数

标准写法：
- `在校人数：26,611人`
- `在校人数：200,000人（推测）`

#### 交通枢纽
G列优先写：
- 日均客流

标准写法：
- `日均客流：70,000人次`
- `日均客流：40,000人次（推测）`

### P5. 真实值优先级

G列取值优先顺序固定为：

1. **直接公开值**
   - 官方网站
   - 官方统计
   - 年报
   - 官方运营数据
   - 官方面向公众的参数页

2. **高可信公开值**
   - 品牌官网
   - Wikipedia / 行业数据库 / 专业场馆库
   - 权威媒体转述的原始数字

3. **保守推测值**
   - 仅当以上两类都不可得时才允许使用
   - 必须显式写 `（推测）`
   - 必须同步写入 `推测留痕`

规则：
- 只要找到稳定公开值，就必须替换原来的 `Unknown`
- 不允许继续保留模板化占位数字
- 不允许把“已知场景很大”写成具体数值而不标 `（推测）`

### P6. Unknown 的保留条件

只有在以下条件同时满足时，G列才允许继续保留 `Unknown（待核验）`：
- 已做过公开搜索
- 未找到稳定可复用的主指标值
- 没有足够依据进行保守推测
- 已在 `方法说明` 或 `推测留痕` 中说明原因

### P7. 与推荐理由的关系

- 推荐理由必须优先基于 G 列主指标生成
- 若 G 列为直接值，则推荐理由优先写直接值
- 若 G 列为推测值，则推荐理由必须保守表达，且不得把推测写成已验证事实

### P8. 与证据表、推测留痕的同步规则

只要 G 列发生更新，必须同步更新：

#### 证据表
- 字段组 = `物业点重要证据`
- 字段值 = G列最新值
- 证据等级 = `已验证 / 已支撑 / 指示性`
- 交叉校验状态 = 与当前证据真实状态一致

#### 推测留痕
若 G 列包含 `（推测）`，必须登记：
- 推测字段 = `物业点重要证据`
- 推测值 = G列值
- 推测依据
- 推测链路
- 推测置信度

### P9. 执行约束

- 不允许把循环数字、模板化占位数、规则生成数列写进 G 列
- 不允许把 proxy 结果冒充主指标
- 不允许只修改主表而不更新证据表与推测留痕
- 不允许 G 列和推荐理由互相矛盾
